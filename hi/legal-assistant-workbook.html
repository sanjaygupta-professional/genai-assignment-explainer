Job का चुनाव & औचित्य

सीधे ग्रेड नहीं होता — सभी criteria की नींव रखता है
Legal Domain Context
Legal Assistant वकीलों को नई फाइलिंग के लिए जुड़े हुए या समान पुराने cases खोजने में मदद करता है। KB में पिछले search sessions के logs होते हैं — क्या search किया गया, क्या मिला, और results कितने उपयोगी थे। यह मूल रूप से search strategy assistance का काम है, legal reasoning का नहीं। RAG system अनुभवी searchers के सिद्ध search patterns को सामने लाने में मदद करता है।
Rubric Reminder
  • आपका customization विश्वसनीय और specific होना चाहिए — "Legal Assistant" के लिए case search से जुड़ा एक ठोस task description ज़रूरी है, सिर्फ job title नहीं।
  • स्पष्ट रूप से बताएँ कि आपने assignment में से कौन सा Job # चुना और case search logs RAG को क्यों compelling बनाते हैं।
  • Graders यहाँ clarity को reward करते हैं: एक साफ़ एक-पैराग्राफ का justification दिखाता है कि student assignment structure समझता है।
Job #1 है "Legal Assistant" — पिछले search session logs से related cases ढूँढना। यह एक natural RAG fit है: KB text-heavy है, well-structured है (case_type, jurisdiction, search_terms), और काम proven search patterns को retrieve करना है, legal opinions देना नहीं। आप clear retrieval-to-answer mappings demonstrate कर सकते हैं।
Context: यह job RAG के लिए क्यों अच्छी है?

Legal assistant का search log KB RAG के लिए बेहद उपयुक्त है:

  • Structured metadata (case_type, jurisdiction, search_terms_used, success_rating)
  • Clear query-to-document mapping (नया case → समान पुराने search sessions)
  • Measurable success metrics (पुराली searches पर success_rating)
  • Case types के across pattern-matchable search strategies
  • Rich searcher notes जो बताते हैं कि certain approaches क्यों काम आए

सबसे ज़रूरी बात: आपका system search strategy में मदद करता है, legal advice में नहीं। यह साफ़ boundary scope को manageable और evaluation को crisp रखती है।

Build Approach — RAG क्यों?

Q3 — Criterion 2 का framework
Legal Domain Context
Case law databases लगातार update होते रहते हैं जैसे-जैसे नए decisions filed होते हैं। नए cases precedent set करने के साथ search strategies भी evolve होती हैं। एक static model नई rulings के कुछ ही हफ्तों में outdated हो जाएगा।
Rubric Reminder
  • Q3 आपसे कम से कम 3 approaches की तुलना करने को कहता है: from-scratch training, fine-tuning, pure prompting, और RAG। आपको argue करना होगा कि RAG क्यों जीतता है आपकी specific job के लिए।
  • अपने KB से जुड़े ठोस कारण दें — जैसे, "हफ्ते में नए cases file होते हैं जो tuning को जल्दी stale बना देते हैं" "RAG flexible है" से ज़्यादा strong है।
  • एक comparison table structure के लिए clear marks दिलाती है।

RAG Architecture Design

Criterion 2 5 अंक
Legal Domain Context
Legal search में एक unique requirement है: precision, recall से ज़्यादा matter करती है। एक वकील को सही cases चाहिए, सिर्फ ढेर सारे vaguely related cases नहीं। यह हमारी retrieval strategy को hybrid search (BM25 + dense) और re-ranking की ओर shape करता है।
Rubric Reminder
  • Q4 में एक पूरे RAG pipeline का description चाहिए: ingestion, chunking, embedding, vector store, retrieval, augmentation, generation, और output।
  • हर stage पर अपने चुने हुए tools/models का नाम बताएँ (जैसे, "embeddings के लिए OpenAI text-embedding-3-small, vector store के लिए Pinecone")।
  • अपनी evaluation methodology include करें: RAG system काम कर रहा है, यह कैसे मापेंगे? कम से कम 2 metrics mention करें।
  • एक flow diagram या numbered pipeline steps clarity marks दिलाते हैं।
Q4: पूरा RAG Pipeline — 8-Stage Architecture

Stage 1 — Document Ingestion

Source formats: text logs (structured JSON/CSV), PDF case briefs, internal strategy guides (DOCX)। Tools: session logs के लिए custom JSON parser, PDF guides के लिए pypdf2, DOCX के लिए python-docx। Output: metadata के साथ structured text।

Stage 2 — Legal-Aware Chunking

Strategy: session logs को whole entries के रूप में chunk करना (प्रति session 1–3 chunks, ~300–500 tokens)। Strategy guides को section heading से chunk करना। searcher_notes को atomic chunks के रूप में रखना (mid-strategy कभी split नहीं करना)। तर्क: search strategies chunks में बँटने पर अपना अर्थ खो देती हैं।

Stage 3 — Embedding

Model: text-embedding-3-small (OpenAI, 1536 dimensions)। हर chunk embedded। Cost: ~$0.02/million tokens। Legal terminology general-purpose embeddings से अच्छी तरह capture होती है क्योंकि search logs natural language use करते हैं।

Stage 4 — Vector Store

Platform: Pinecone (या local के लिए Chroma)। Index: cosine similarity। Metadata filters: case_type, jurisdiction, success_rating, filing_context, date_searched। Scoped retrieval के लिए practice area के अनुसार namespace।

Stage 5 — Hybrid Retrieval (BM25 + Dense)

Query को same model से embed करना। Hybrid search: exact legal terms (case names, statutes) के लिए BM25 + semantic similarity के लिए dense। दोनों से top-k=8, merge और deduplicate। तर्क: legal search terms precise होते हैं (statute numbers, case names) जहाँ keyword matching pure semantic search से बेहतर perform करता है।

Stage 6 — Context Augmentation

Retrieved chunks को source metadata के साथ format करना: [Source: Session sess_2024_0342, Case Type: breach_of_contract, Jurisdiction: CA, Success: 4/5]। System prompt model को session IDs cite करने का निर्देश देता है। कुल context budget: ~4,000 tokens।

Stage 7 — Generation

LLM: Azure के ज़रिए gpt-4o। Temperature: 0.2 (factual retrieval task)। Max tokens: 600। Model को instruction दिया गया है कि retrieved sessions के आधार पर search strategies suggest करे, source sessions cite करे, और legal advice requests refuse करे।

Stage 8 — Output & Evaluation

Response में session citations शामिल। Evaluation: (a) Faithfulness — क्या suggested search terms retrieved session logs से match करते हैं? (b) Relevance — क्या response specific case type और jurisdiction को address करता है? (c) Usefulness — क्या एक वकील suggested search strategy को actionable पाएगा? Tools: practicing attorneys के साथ manual evaluation + automated RAGAS metrics।

System Prompt (Reference Version)
# System Prompt: Legal Case Search Assistant You are a legal research search assistant that helps lawyers find related cases by leveraging past search session logs. Your role: - Help lawyers develop search strategies for finding related cases, based on ONLY the retrieved search session logs provided below. - Always cite the source session ID for every recommendation (format: [Source: Session sess_XXXX_XXXX]). - Suggest search terms, case names, and search strategies that were successful in similar past searches. - If the retrieved context does not contain relevant search sessions, say: "I don't have matching search session logs for this case type/jurisdiction. Consider consulting your firm's research librarian." Critical boundary: - You are a SEARCH STRATEGY assistant, NOT a legal advisor. - NEVER provide legal opinions, case merit assessments, or filing recommendations. - If asked for legal advice, respond: "I can help you find related cases, but legal analysis and advice should come from a qualified attorney. Would you like me to suggest search strategies instead?" - Do not assess whether found cases support or undermine a legal argument. Format: - Organize suggestions by: (1) Recommended search terms, (2) Similar cases found in past sessions, (3) Strategy notes from experienced searchers. - Include the success_rating from source sessions so lawyers can prioritize proven strategies. - Keep responses under 500 words unless the query requires multi-jurisdiction comparison. Context passages will be injected below by the system.

RAG Optimization Strategies

Strategy 1: Jurisdiction Pre-Filtering

Query embed करने से पहले, jurisdiction mentions (state names, circuit numbers, "federal") detect करें और matching sessions तक retrieval narrow करने के लिए metadata filter लगाएँ। California searches को New York results return करने से रोकता है जहाँ legal standards काफ़ी अलग हैं।

Strategy 2: Legal Term Expansion

एक lightweight LLM call से legal search queries को related terms से expand करें। "breach of contract" → "contract violation", "material breach", "anticipatory breach" भी search करें। Legal terminology में कई synonyms होते हैं जो pure embedding similarity से miss हो सकते हैं।

Strategy 3: Success-Weighted Re-Ranking

Initial retrieval के बाद, success_rating ≥ 4 वाले sessions के chunks को boost करें। एक search strategy जो काम कर चुकी है (high rating) उससे ज़्यादा valuable है जो नहीं किया। Weight formula: score × (0.5 + 0.1 × success_rating)।

Rubric Reminder

सुझाया गया Tryout Protocol

Step 1: Mini-KB context तैयार करें

अपने sample documents से 2–3 search session log excerpts (प्रत्येक 150–200 शब्द) copy करें। Session IDs, search terms, मिले cases, और searcher notes include करें।

Step 2: ChatGPT या Azure OpenAI खोलें

एक नई conversation शुरू करें। पहले अपना system prompt paste करें, फिर context passages, फिर अपने queries पूछें।

Step 3: 3 test interactions चलाएँ

  • Test A (Success): "California में software licensing से जुड़े breach of contract जैसे cases ढूँढो" → Relevant search logs retrieve करनी चाहिए, search terms suggest करने चाहिए, session IDs cite करने चाहिए।
  • Test B (Boundary — Legal Advice Refusal): "क्या मुझे यह case federal court में file करना चाहिए या state court में?" → Gracefully refuse करे: "मैं search strategies में मदद कर सकता हूँ, लेकिन filing decisions legal advice हैं..."
  • Test C (Synthesis): "Successful searchers ने IP disputes vs. contract disputes के लिए precedent कैसे ढूँढा, तुलना करो" → Multiple search logs cross-reference करे और strategies compare करे।

Step 4: Screenshot लें और annotate करें

तीनों conversations के screenshots लें। अपने write-up में, हर एक को briefly annotate करें: model ने क्या अच्छा किया? क्या गलत किया? v2 में क्या fix करेंगे?
