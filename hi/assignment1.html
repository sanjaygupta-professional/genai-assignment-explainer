5 सवाल जो आपको ज़रूर answer करने हैं

Q1: GenAI कितना मदद कर सकता है? (पूरी तरह / ज़्यादातर / कुछ हद तक / बहुत कम)

आपको एक चुनना है: (a) पूरी तरह 100%, (b) ज़्यादातर 80%+, (c) कुछ हद तक 40%+, या (d) बहुत कम <20%।

अपनी Choice को कैसे Justify करें

  • Task को sub-tasks में तोड़ें। हर एक के लिए assess करें: क्या GenAI यह कर सकता है? कितनी अच्छी तरह?
  • Human-only हिस्से पहचानें: judgment calls, ethical decisions, physical actions, real-time social cues।
  • Specific रहें: “GenAI similar cases retrieve कर सकता है और search terms suggest कर सकता है (70% काम), लेकिन legal applicability verify करना और final case selection इंसान को करना होगा (30%).”
“पूरी तरह” तब तक न चुनें जब तक आप सच में 100% automation defend न कर सकें। ज़्यादातर jobs में human oversight ज़रूरी है। “ज़्यादातर” अधिकांश choices के लिए safe sweet spot है — यह दिखाता है कि आप GenAI की power समझते हैं साथ ही real-world limits भी।
उदाहरण — Legal Assistant
Similar cases ढूंढना: “ज़्यादातर (80%+)। RAG के साथ GenAI past search logs search कर सकता है, successful queries में patterns पहचान सकता है, relevant search terms suggest कर सकता है, और case similarity rank भी कर सकता है। हालांकि, legal relevance verify करना, jurisdictional applicability check करना, और returned cases currently good law हैं यह validate करना इंसान को ही करना होगा।”
Q2: GenAI इस task के लिए क्या कर सकता है vs क्या नहीं?

एक clear two-column analysis बनाएं:

GenAI यह कर सकता हैGenAI यह नहीं कर सकता
Semantic similarity के basis पर relevant KB documents retrieve करना Professional judgment या ethical reasoning करना
Multiple sources की information को coherent responses में synthesize करना Human verification के बिना factual accuracy guarantee करना
Historical data में patterns पहचानना ऐसी novel situations handle करना जिनका KB में कोई precedent नहीं
Past expert behavior के basis पर next steps suggest करना Real-time contextual nuances (tone, urgency, politics) समझना
सबसे मज़बूत answers में हर “नहीं कर सकता” item को एक specific mitigation strategy से जोड़ा जाता है। उदाहरण: “GenAI accuracy guarantee नहीं कर सकता → हम confidence score add करते हैं और 0.8 threshold से नीचे responses के लिए human-in-the-loop review रखते हैं।”
Q3: Build approach — From scratch, fine-tuning, prompting, या RAG?

Assignment strongly hint करता है कि RAG expected answer है — यह title और problem statement में है। लेकिन आपको फिर भी justify करना चाहिए कि alternatives की जगह RAG क्यों:

Approachकब काम करता हैयहां क्यों नहीं
From scratch Unique language/domain, massive data, unlimited budget बहुत expensive, millions of examples चाहिए, solved problems को reinvent करता है
Fine-tuning Narrow domain style, consistent output format ज़रूरी हो KB updates के लिए retraining ज़रूरी; evolving knowledge के साथ scale नहीं करता
Prompting only General knowledge tasks, proprietary data की ज़रूरत नहीं KB access नहीं कर सकता; context window से limited; domain-specific knowledge नहीं
RAG Domain-specific KB, current data चाहिए, explainability important यही answer है — KB solution का centerpiece है
भले ही RAG expected है, mention करें कि आप approaches combine कर सकते हैं: retrieval के लिए RAG + response quality के लिए prompt engineering + domain-specific language के लिए potential fine-tuning। यह sophistication दिखाता है।
Q4: Conceptual RAG architecture design

यह आपके assignment का core है — पूरी visual guide के लिए Section 6: RAG Architecture Primer देखें। आपके design में ये cover होने चाहिए:

  1. Document ingestion: KB documents को कैसे chunk, embed, और index किया जाएगा
  2. Query pipeline: User queries कैसे embedding → retrieval → context injection → LLM generation से flow करेंगी
  3. Tool choices: Specific embedding models, vector DBs, LLMs, orchestration frameworks
  4. Prompt design: System prompts, few-shot examples, output format instructions
  5. Evaluation method: आप कैसे measure करेंगे कि solution actually काम करता है या नहीं
Criterion 2 का rubric explicitly कहता है: “the method of estimating the success of the approach is also clearly stated.” बहुत से students architecture describe करते हैं लेकिन यह बताना भूल जाते हैं कि उसे evaluate कैसे करेंगे। Retrieval precision, answer relevance scores, या user satisfaction ratings जैसे metrics शामिल करें।
Q5: Limitations और risks

Assignment specifically TCO और response time mention करता है। ये categories cover करें:

  • Cost (TCO): Embedding computation, vector DB hosting, हर query पर LLM API costs, KB maintenance
  • Performance: Latency (embedding + retrieval + generation), concurrent users के लिए throughput
  • Quality risks: Hallucination, retrieval failures, outdated KB, historical data में bias
  • Operational risks: Data privacy, KB curation effort, model deprecation, vendor lock-in
  • Domain-specific risks: आपके chosen job से specific जो भी हो (जैसे Legal Assistant के लिए legal liability)
सिर्फ risks list मत करें — हर एक के लिए mitigations propose करें। “Hallucination risk → हर response में source citations include करके और high-stakes decisions के लिए human review require करके mitigate किया जाएगा।” यह weakness को आपके answer में strength बना देता है।

छिपी हुई Requirement: Evaluation Methodology

ध्यान दें rubric कहता है “the method of estimating the success of the approach is also clearly stated.” यह सबसे commonly miss किया जाने वाला element है। ये शामिल करें:

  • Retrieval metrics: Precision@k, Recall@k, MRR (Mean Reciprocal Rank)
  • Generation quality: Faithfulness score (क्या answer retrieved context से match करता है?), relevance, completeness
  • End-to-end: User satisfaction ratings, task completion time comparison (GenAI के साथ vs बिना)
एक beautiful architecture diagram बनाना लेकिन कोई evaluation plan नहीं, guaranteed 3 है 5 की जगह। हमेशा शामिल करें: “हम इस solution को evaluate करेंगे...”

स्कोरकैसा दिखता है
अच्छा (5-4)Technically correct solution जिसमें effective prompt design और RAG optimization strategies हैं

“Technically Correct” का मतलब क्या है

  • Prompts: Actual system prompts दिखाएं जिनमें role definition, instructions, और output format हो। कम से कम एक few-shot example शामिल करें।
  • RAG enhancements: कम से कम 2-3 strategies mention करें: hybrid search (keyword + semantic), re-ranking, query expansion, metadata filtering, chunk overlap strategy।
  • Correct pipeline: Technical flow make sense करता हो — आप queries को एक model से embed नहीं कर रहे और documents को किसी दूसरे incompatible model से।

ऐसी Limitations जो Impress करती हैं

  • Quantified costs: “GPT-4o-mini के ~$0.01/1K tokens और 500 queries/day पर, monthly LLM costs ≈ $150 + vector DB hosting ≈ $50/month.”
  • Specific latency: “Expected response time: 2-4 seconds (embedding 200ms + retrieval 300ms + LLM generation 1.5-3s).”

Limitations को “Limitation → Mitigation” format में frame करें। यह maturity दिखाता है। Grader देखता है कि आप problem space को deeply समझते हैं, सिर्फ concerns list नहीं कर रहे।

Step-by-Step Solution गाइड

1   अपनी Job समझदारी से चुनें

सभी jobs के लिए RAG solution design करना equally आसान नहीं है। ऐसी jobs को priority दें जहां:

  • KB text-based हो (transcripts, logs, documents — videos या images नहीं)
  • Task में information retrieval और synthesis शामिल हो (creative generation नहीं)
  • एक clear expert-to-novice knowledge transfer story हो

Recommended Picks (RAG Design के लिए सबसे आसान)

JobRAG के लिए क्यों अच्छी हैकठिनाई
Legal Assistant (#1)Text-heavy logs, clear retrieval task, well-defined success criteriaEasy
Insurance Underwriter (#4)Structured claims data, decision patterns, obvious KB schemaEasy
HR Executive (#7)Negotiation transcripts, pattern matching, practical sample queriesMedium
Bank Executive (#2)Conversation transcripts, FAQ-style retrievalEasy
2   अपना Knowledge Base डिज़ाइन करें

यह Criterion 1 (20%) है। आपका KB design specific और believable होना चाहिए:

KB Design Template

// अपना document schema define करें Document Type: [जैसे "Past search session log"] Fields: - id: Unique identifier - date: Session कब हुआ - domain_field_1: [Job-specific field] - domain_field_2: [Job-specific field] - expert_notes: Expert के free-text notes - outcome: Success/failure + details - tags: Filtering के लिए categorical labels Volume: ~5,000 documents, 50/month बढ़ रहे हैं Avg Size: 500-2,000 words प्रति document Update Frequency: Weekly batch ingestion Format: JSON documents [vector DB] में stored

Sample Queries (3-5 का target रखें)

अपनी queries को type से vary करें:

  • Simple lookup: “पिछले साल के similar cases दिखाओ।”
  • Analytical: “इस तरह के cases में successful outcomes को क्या patterns distinguish करते हैं?”
  • Procedural: “एक expert इस type के case को कैसे approach करता, step by step बताओ।”
  • Comparative: “यह case [reference case] से कैसे अलग है?”
एक ऐसी query include करें जो system के लिए मुश्किल हो — और बताएं क्यों। यह depth दिखाता है: “Query 5 में multiple documents cross-reference करना और temporal reasoning ज़रूरी है, जो single-retrieval RAG की limits को push करता है।”
3   Sample Queries और Expected Responses डिज़ाइन करें

हर query के लिए sketch करें कि एक अच्छा response कैसा दिखेगा। यह grader को दिखाता है कि आपने end-to-end experience सोचा है।

Insurance Underwriter — Query और Expected Response
Query: “इस तरह के claims के कौन से parts reject होने चाहिए?”

Expected Response: “हमारे KB में 23 similar claims (property damage, commercial, California jurisdiction) के basis पर:
1. आम तौर पर rejected: Pre-existing damage claims (similar cases में 78% बार rejected) — देखें claims #UC-2023-0891, #UC-2023-1204
2. Review के लिए flagged: Comparable market rates से 150% ज़्यादा excessive repair estimates (45% cases में flagged)
3. Documentation gap: Vandalism claims के लिए missing police report (policy section 4.2 के अनुसार required)
Note: ये historical decisions के patterns हैं। हमेशा current policy guidelines से verify करें।”

RAG Architecture Primer

यह section आपको RAG pipeline confident तरीके से design करने की technical foundation देता है। Assignment में अपने architecture diagram के basis के रूप में इसे use करें।

Document Ingestion Pipeline

Ingestion के लिए Key Decisions

  • Chunking strategy: Recursive character splitting paragraph boundaries preserve करता है। Context boundaries पर lost न हो इसके लिए 500-1000 tokens per chunk 100-token overlap के साथ use करें।
  • Metadata: Filtered retrieval के लिए हर chunk के साथ document-level metadata (date, category, author) store करें।
  • Embedding model: OpenAI का text-embedding-3-small (1536 dimensions) $0.02/million tokens पर strong quality offer करता है।

Query Pipeline

RAG Enhancement Strategies

Depth demonstrate करने के लिए (Criterion 3) अपने assignment में इनमें से 2-3 mention करें:

1. Hybrid Search (Keyword + Semantic)

Better retrieval के लिए BM25 (keyword matching) को vector similarity के साथ combine करें। तब useful है जब queries में specific IDs, names, या legal terms हों जो pure semantic search miss कर सकता है।

2. Query Expansion

Retrieval से पहले user की query expand करने के लिए LLM use करें: “Find related cases” → “Find related cases involving patent infringement, software claims, prior art challenges.”

3. Re-Ranking

Initial vector search से top-20 results आने के बाद, relevance के लिए उन्हें re-rank करने के लिए cross-encoder model use करें। LLM को ज़्यादा precise top-5 मिलता है, answer quality improve होती है।

4. Metadata Filtering

Vector search से पहले या दौरान metadata (date range, category, jurisdiction) से retrieval filter करें। Noise कम होता है और relevance improve होती है।

RAG के लिए Prompt Engineering

आपके system prompt में ये elements शामिल होने चाहिए:

# RAG के लिए System Prompt Template ROLE: You are a [job title] assistant helping new employees at [company type]. Your role is to [specific task]. CONTEXT RULES: - Use ONLY the provided context to answer questions - If the context doesn't contain relevant information, say so clearly - NEVER fabricate information not present in the context - Cite specific document IDs when referencing KB content OUTPUT FORMAT: - Begin with a direct answer to the query - Support with 2-3 specific examples from the KB - Include confidence level (high/medium/low) - End with suggested next steps for the employee CONSTRAINTS: - [Domain-specific guardrails, जैसे "Do not provide legal advice"] - [Escalation criteria, जैसे "For queries involving amounts over $X, recommend supervisor review"]
Assignment में अपना actual system prompt include करें — यह prompt engineering skill का tangible evidence है। एक simple, well-structured prompt भी “हम appropriate prompting use करेंगे” जैसे vague descriptions से ज़्यादा score करता है।

Scoring Maximizer Checklist

Submit करने से पहले यह checklist use करें। हर item उससे map करता है जो rubric reward करता है।

Criterion 1: KB और Sample Queries 5 अंक
  • 4+ fields वाला clear document schema define किया
  • एक sample KB document include किया (छोटा JSON/table example भी चलेगा)
  • KB volume, average document size, और update frequency बताई
  • 3+ diverse sample queries दिए (simple, analytical, procedural)
  • बताया कि यह KB format chosen task के लिए क्यों serve करता है
Criterion 2: Overall Solution Design 5 अंक
  • पूरी RAG pipeline (ingestion + query) draw या describe की
  • हर component के लिए specific tools name किए (embedding model, vector DB, LLM, framework)
  • Alternatives (from scratch, fine-tuning, prompting) की जगह RAG क्यों, justify किया
  • Specific metrics के साथ evaluation methodology describe की
  • System को कैसे test/validate करेंगे, बताया
Criterion 3: Prompts और RAG Enhancement 5 अंक
  • Actual system prompt include किया (सिर्फ “हम एक prompt लिखेंगे” नहीं)
  • 2+ RAG enhancement strategies describe कीं (hybrid search, re-ranking, query expansion, etc.)
  • Chunk size के reasoning के साथ chunking strategy बताई
  • Technical flow internally consistent है (docs और queries के लिए same embedding model)
  • Prompt में few-shot examples या output formatting mention किए
Criterion 4: Limitations 5 अंक
  • अलग-अलग categories में 4+ specific limitations identify कीं
  • TCO estimate include किया (approximate भी चलेगा — “500 daily queries के लिए $100-300/month”)
  • Response time estimate include किया (“2-4 seconds end-to-end”)
  • Chosen job के domain-specific risks mention किए
  • हर limitation के लिए mitigations propose किए
Criterion 5: Try करके देखें 5 अंक
  • Actually किसी platform पर solution run किया (ChatGPT, Azure OpenAI, Colab, LangChain)
  • कम से कम 2-3 sample queries से test किया
  • Interaction दिखाते screenshots include किए
  • Screenshots पर annotations लगाए जो बताएं कि RAG system हर step पर क्या करता है
  • 3 available screenshot pages में से 2+ इस section के लिए use किए
General Quality
  • 7+3 page limit के अंदर रहे
  • Rubric criteria से match करते clear section headings use किए
  • सभी assumptions explicitly state किए
  • Technical accuracy के लिए proofread किया (correct model names, framework APIs)
